**Знайдені дефекти та ризики під час перевірки:**

1. **Ризик: застарілі та мінливі тарифи хмарних платформ**
   - _Проблема:_ Хмарні платформи часто скасовують або зменшують безкоштовні тарифи (наприклад, Fly.io відмовився від постійного безкоштовного тарифу, Railway перейшов на вичерпні пробні кредити).
   - _Зменшення:_ Проведено дослідження станом на листопад 2026 року; чітко зафіксовано дату; у документації запропоновано повністю безкоштовну зв'язку Render Free + Neon Serverless PostgreSQL та задокументовано резервний план на базі Railway.
2. **Ризик: компіляція native-модуля argon2 на Windows**
   - _Проблема:_ Модуль `argon2` використовує C++ розширення, що на Windows без Visual Studio Build Tools може викликати помилки інсталяції.
   - _Зменшення:_ Перевірено та зафіксовано в архітектурі, що сучасні версії npm-пакета `argon2` (v0.31+) постачають prebuilt binaries для платформи Windows x64. Додатково передбачено безпечний fallback на `bcrypt` / `bcryptjs` у разі проблем зі збиранням.
3. **Ризик: строга політика CSP 'self' та потенційні inline styles/scripts у клієнті**
   - _Проблема:_ Якщо існуючий клієнт (з Лаб 3-4) містить випадкові атрибути `style="..."` або інлайн-обробники `onclick`, заголовок CSP заблокує їх виконання.
   - _Зменшення:_ У вимогах та архітектурі суворо підтверджено правило повної відсутності інлайн-стилів та інлайн-скриптів. На етапі Фази 1 буде проведено валідацію клієнтських HTML-файлів перед підключенням CSP.
4. **Ризик: масове присвоєння сторонніх полів (Mass Assignment Vulnerability)**
   - _Проблема:_ Без суворої валідації запитів зловмисник може передати сторонні поля (наприклад, `userId` іншого користувача або службові прапорці).
   - _Зменшення:_ Зафіксовано обов'язкове використання методу `.strict()` у схемах Zod валідації, що повертає статус `400 Bad Request` при передачі невідомих полів.
5. **Ризик: засинання та холодний старт безкоштовних інстансів (Cold Starts)**
   - _Проблема:_ Render зупиняє контейнер після 15 хвилин бездіяльності; Neon також призупиняє обчислювальні вузли (compute units). Перший запит може тривати до 30-50 секунд.
   - _Рішення після деплою (Фаза 4):_ ранню пораду про cron-пінг до `/api/health` скасовано. Періодичний запит будив би Render і Neon та витрачав би безкоштовні квоти; прийнято автоматичне засинання й холодний старт.

9. `docs/api-examples.http`, `docs/phases/phase1.md`.

**Знайдені дефекти та ризики під час перевірки:**

1. **Дефект: парсинг дат у Zod без прив'язки до UTC (Timezone rollover)**
   - _Проблема:_ Вираз `new Date(val + 'T00:00:00')` у часовому поясі UTC+2 інтерпретував дату локально, через що `toISOString().slice(0, 10)` повертав попередній календарний день (`2027-01-14` замість `2027-01-15`), спричиняючи помилку 422 валідації дедлайну для коректних дат.
   - _Виправлення:_ Змінено на `new Date(val + 'T00:00:00Z')`, що гарантує валідацію в часовому поясі UTC незалежно від регіональних налаштувань хоста.
2. **Дефект: несумісність імпорту Vitest у CommonJS (CJS)**
   - _Проблема:_ Оскільки Vitest 2.x поставляється як суто ESM-пакет, прямий виклик `require('vitest')` у CJS-файлах тестів викидав виняток `Vitest cannot be imported in a CommonJS module using require()`.
   - _Виправлення:_ Увімкнено `globals: true` у `vitest.config.mjs`, а директиви `require('vitest')` видалено; тестові глобали інжектуються автоматично Vitest та задекларовані для ESLint.
3. **Дефект: валідація PORT:0 у конфігурації для тестів**
   - _Проблема:_ `src/config.js` містив правило `z.number().positive()`, що викликало помилку при передачі `PORT=0` для динамічного вибору порту в тестах.
   - _Виправлення:_ Змінено на `.min(0)`.
4. **Помилки лінтера ESLint: невикористані змінні та відсутній глобал URL**
   - _Проблема:_ У файлі `tests/helpers/db.js` були залишені невикористаний імпорт `execSync` та змінна `migrateScript`; у `originCheck.js` використовувався `URL`, не зареєстрований у списку глобалів `eslint.config.mjs`.
   - _Виправлення:_ Вилучено невикористані змінні, зареєстровано `URL` та `URLSearchParams` у конфігурації лінтера.

## 3. Ризики ШІ-згенерованого коду та як їх зменшено

У процесі розробки full-stack веб-додатків генеративними моделями ШІ існують типові ризики, які вимагають систематичного архітектурного контролю:

| Категорія ризику                             | Конкретний приклад у проекті                                                                                                   | Заходи щодо зменшення (Mitigation)                                                                                                                                                                     |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Витік секретів у репозиторій**             | Hard-coded паролі бази даних чи секрети сесій у файлах конфігурації або seed-скриптах                                          | Усі конфіденційні дані передаються лише через змінні оточення; файл `.env` внесено у `.gitignore`; у репозиторій додається лише безпечний `.env.example`; сканування історії Git на наявність витоків. |
| **Застарілі або вигадані API**               | Використання неіснуючих тарифів (наприклад, безкоштовний Postgres на Fly.io) або застарілих сигнатур методів Node.js           | Перевірка документації станом на кінець 2026 року; фіксація дати дослідження; тестування актуальності бібліотек.                                                                                       |
| **Небезпечні налаштування за замовчуванням** | Обрізання довгих паролів у застарілому `bcrypt` (ліміт 72 байти), сесійні cookie без прапорця `HttpOnly` або з `SameSite=None` | Використання сучасного алгоритму `argon2id`; явне примусове конфігурування прапорців `HttpOnly`, `SameSite=Lax`, `Secure` для cookie.                                                                  |
| **Відсутність або слабка валідація**         | Прийняття довільних JSON-полів, неперевірені дати (наприклад, `31.02.2026`) чи переповнення пам'яті великим body               | Бібліотека Zod із суворим режимом `.strict()`; обов'язкова перевірка календарних дат; обмеження розміру тіла запиту у 16 КБ (`express.json({ limit: '16kb' })`).                                       |
| **Надмірна складність (Over-engineering)**   | Пропозиція розгортати мікросервіси, брокери повідомлень (RabbitMQ) або окремий сервер Redis для сесій студента                 | Архітектура побудована як моноліт із єдиним походженням (Single-Origin Monolith); сесії зберігаються у таблиці `sessions` PostgreSQL — просто, надійно та повністю достатньо для навчального проекту.  |
| **Ліцензійна чистота залежностей**           | Випадкове додавання пакетів із рестриктивними ліцензіями (GPL/AGPL) у комерційний або відкритий проект                         | Використання пакетів виключно з дозвільними ліцензіями MIT або ISC (`express`, `pg`, `argon2`, `zod`, `helmet`); автоматичний аудит ліцензій.                                                          |
| **SQL-ін'єкції**                             | Конкатенація рядків у запитах пошуку `q` або фільтрації                                                                        | Використання виключно параметризованих SQL-запитів (`$1, $2, ...`) через офіційний драйвер `pg`; автоматизовані тести з ін'єкційними пейлоадами (`' OR 1=1; --`).                                      |
| **Міжсайтовий скриптинг (XSS)**              | Вставка повернутих користувацьких даних у DOM через `element.innerHTML`                                                        | Клієнтська частина оперує виключно безпечними властивостями `element.textContent` та створенням вузлів через `document.createElement`; CSP заголовок `script-src 'self'`.                              |
